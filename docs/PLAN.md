# 暗夜精灵 · 规划

> 术语以 [`CONTEXT.md`](../CONTEXT.md) 为准；关键架构决策见 [`docs/adr/`](./adr/)。

## 1. 产品定义

**一句话**：一个只给自己用的 macOS 桌面工具，在一张自由画布上，用 AI 把"产品主题"一路推进成 APP / 桌面应用的高保真页面。

| 项 | 决定 |
|---|---|
| 定位 | AI 生图编排画布，不做矢量设计编辑器（ADR 0002） |
| 用户 | 仅自己，纯本地，无账号、无云、无协作 |
| 平台 | 仅 macOS |
| 项目 | 一个目录 = 一个项目，一个项目一张画布（ADR 0003） |
| 技术栈 | Electron + React + TypeScript + PixiJS（ADR 0001） |
| AI | 可替换的模型供应商接口，第一版只接 OpenAI |
| 交付物 | 高保真页面 PNG + 素材包 + 分层 SVG（可导入 Figma） |
| 界面 | 只做深色主题 |

**明确不做**：矢量绘制、自动布局、组件系统、多人协作、云同步、Windows/Linux。

## 2. 核心流程（第一版验收用例：日式寿司点餐）

1. 新建项目目录。
2. 在**助手**里输入"日式寿司点餐"，生成**主题卡**（关键词、视觉线索、色板、造型/材质/光影规则），设为**生效主题卡**。
3. 导入 Banner 风格**参考图** → 助手反推出**提示词卡** → 连线绑定 → **生成** Banner，挑一个**当前版本**。
4. 四个金刚位（热门寿司 / 今日上新 / 店长推荐 / 全部菜单）：照片参考图 → 生成简笔画**图像卡** → 再生成 3D 图像卡，每步靠**来源连线**串起来。
5. 导入首页**低保真原型** → 建**页面框** → 把 Banner 和四个金刚位拖进去调整大小与位置。
6. 导出首页 PNG、素材包、分层 SVG；把 SVG 导入 Figma，确认图层结构完整。

生效主题卡的规则会自动附加到第 3、4 步的每一次生成里，可以单次关闭。

## 4. 架构

```
┌───────────────── Electron 主进程 ─────────────────┐
│ 项目读写（原子写入） · 钥匙串（safeStorage）        │
│ AI 供应商调用（API Key 不进渲染进程） · 生成队列     │
└──────▲──────────────────────────────▲─────────────┘
       │ IPC（类型化）                  │ MessagePort
┌──────┴──────── 渲染进程 ───────┐  ┌───┴──── 图片工作进程（utilityProcess）────┐
│ React：工具栏/面板/助手/队列    │  │ 解码 · 多级缩略图 · 导出 PNG/SVG/素材包   │
│ 画布状态仓库（普通 TS，非 React）│  └────────────────────────────────────────┘
│ PixiJS：图像卡/卡片/连线/选框   │
└──────────────────────────────┘
```

### 4.1 渲染与状态分离

- **画布状态仓库**是一个与 React 无关的 TypeScript 对象，持有所有画布对象和视口状态。
- **PixiJS** 直接订阅仓库、直接渲染；拖拽、缩放、平移每帧只改仓库和 Pixi 对象，**不触发 React 渲染**。
- **React** 只订阅"选中对象"和"低频状态"（比如面板内容、队列），用选择器避免无关更新。
- 所有改动都走**命令**（`MoveCommand`、`SetCurrentVersionCommand`……），同一套命令同时驱动撤销重做和自动保存。

### 4.2 纹理分级

| 级别 | 长边 | 何时使用 |
|---|---|---|
| L0 | 256px | 缩小到全景、对象屏幕尺寸 < 256px |
| L1 | 1024px | 常规浏览 |
| L2 | 原图，切成 1024 的块 | 放大到对象屏幕尺寸 > 1024px |

- 缩略图和 L2 切块由图片工作进程在导入或生成完成时预先生成，存在 `.cache/`（ADR 0004）。
- 纹理在提交时主动上传到 GPU，每帧最多上传约 6MB（一张 L1 或一块 L2），不会拖到首次上屏那一帧集中上传。
- L1 + L2 的显存预算为 768MB，超出时按最近最少使用原则卸载；L0 常驻；视口外的对象只要 L0。
- 关闭 PixiJS 自带的纹理回收，纹理的生命周期完全由纹理管理器负责。
- 切换级别时先显示已有的纹理，不出现白块；L2 不生成 mipmap，因此不需要 L2 时也不会优先选用它。

### 4.3 AI 供应商接口

```ts
interface ModelProvider {
  describeImage(images: ImageRef[], instruction: string): Promise<string>;      // 反推提示词
  generateImage(prompt: string, images: ImageRef[], n: number): Promise<Blob[]>; // 生图 / 改图
  estimateCost(request: GenerateRequest): Money;
}
```

- 第一版只实现 `OpenAIProvider`。
- 生成队列在主进程里，有并发上限，可以取消；失败可以重试，失败原因显示在队列里。
- 发给模型的最终提示词 = 提示词卡正文 + 生效主题卡规则（可单次关闭）。实际发送的全文记在版本元数据里，方便以后复现。

## 5. 数据

### 5.1 项目目录

```
寿司点餐/
├── project.json        # 画布结构：所有对象、连线、视口、生效主题卡
├── .gitignore          # 新建项目时写入，忽略 .cache/
├── assets/             # 原图：导入的参考图、低保真原型、每个生成版本
│   └── <版本id>.png / .jpg / .webp
├── exports/            # 导出产物
└── .cache/             # 可随时删除重建的缩略图和 L2 切块
    └── <版本id>@256.webp, @1024.webp, @tile-<x>-<y>.webp, <版本id>.json（缓存完整的标记）
```

- 导入时 PNG / JPEG / WebP 原样复制；其他格式和带 EXIF 旋转的图统一转成方向正确的 PNG。
- L2 长边超过 4096 的原图先等比缩到 4096 再切块，原图本身不动。
- 打开项目后后台逐个检查缓存标记，缺了就从原图重建，重建好后画布和面板自动刷新。

**M1 实际落地的结构**（后续里程碑在 `cards` 旁边加新的对象类型）：

```ts
type ProjectFile = {
  schemaVersion: 1;
  regions: Region[];          // { id: 'theme' | 'assets' | 'pages', name, x, y, width, height }
  cards: ImageCard[];         // 数组顺序即绘制顺序
  viewport: { originX; originY; zoom } | null;
};
type ImageCard = { kind: 'image'; id; name; x; y; width; height; versions: Version[]; currentVersionId };
type Version = { id; file; width; height; createdAt; origin: 'import'; sourceName? };
```

读入时逐项校验：坏掉的图像卡跳过并提示，指向项目目录以外的路径直接拒绝，版本号不认识时拒绝打开而不是去猜。

### 5.2 `project.json` 结构草图

```ts
type CanvasObject =
  | ImageCard      // 图像卡：{ id, frame, versions: Version[], currentVersionId, sourceLinks }
  | PromptCard     // 提示词卡：{ id, frame, text, imageBindings: { slot: number; imageCardId }[] }
  | ThemeCard      // 主题卡：{ id, frame, topic, keywords, cues, palette, rules }
  | PageFrame      // 页面框：{ id, frame, lowFiImageCardId, devicePreset?, placements: Placement[] }
  ;

type Version = {
  id: string; file: string; createdAt: string;
  promptSnapshot: string;      // 实际发送给模型的全文
  sourceVersionIds: string[];  // 生成时上游的版本，第二版用来判断"已过期"
  cost?: Money;
};

type Placement = { imageCardId: string; frame: Rect; lockedVersionId?: string };

type Project = {
  schemaVersion: 1;
  activeThemeCardId?: string;
  regions: Record<'theme' | 'assets' | 'pages', Rect>;
  objects: CanvasObject[];
  viewport: { x: number; y: number; zoom: number };
};
```

- 写盘：改动后约 300ms 防抖，先写 `project.json.tmp`，再原子重命名。
- 打开项目时校验 `assets/` 里的文件，缺失的显示成"缺失"占位，不会崩溃。
- 撤销"生成"只会把当前版本切回去，已生成的版本永远留在版本栈里。

## 6. 性能预算

| 指标 | 目标 |
|---|---|
| 画布规模 | 200 张 2K 图（实际一个项目 50–100 张） |
| 平移 / 缩放 | 稳定 120fps（ProMotion），最差不低于 60fps |
| 拖拽延迟 | 少于 1 帧 |
| 打开项目（应用已启动） | 少于 1 秒出现可交互画布，先显示 L0 |
| 导入 / 生成完成后的缩略图 | 不阻塞画布，后台完成 |

Rust 只在实测发现瓶颈时才引入，比如图片工作进程的处理速度不够。

## 7. 里程碑

### M0 画布性能原型 ✅
Electron + React + PixiJS 空壳；随机放 200 张 2K 图；实现缩放、平移、框选、拖拽和三级纹理。
**验收**：用帧率面板实测，满足第 6 节的全部指标。不达标就先调整架构，再进入 M1。

**怎么验证**

| 命令 | 作用 |
|---|---|
| `npm run dev` | 开发模式，手动试用 |
| `npm run bench` | 自动跑 5 个场景（开 vsync），打印报告并判定是否达标 |
| `npm run bench:uncapped` | 关掉 vsync，只看渲染吞吐量，不判定卡顿 |
| `npm run selftest` | 验证 sharp 在 Electron 工作进程里可用 |
| `npm run pack` | 打本地 .app，可用 `暗夜精灵.app/Contents/MacOS/暗夜精灵 --self-test` 再验一次 |

卡顿判定：开 vsync 时，每个场景里**最慢一帧**的 CPU 耗时都不超过 8.33ms，且超过 20ms 的帧间隔少于 1%。开发机只有 60Hz 屏，所以用每帧 CPU 耗时来推断 120Hz 下的表现。

**结果（Apple M4，60Hz 外接屏）**

| 场景 | 最慢一帧 CPU（多次运行） |
|---|---|
| 全景浏览（L0） | 1.1–1.7ms |
| 中景快速平移（持续加载 L1） | 1.4–5.1ms |
| 全景 ↔ L2 往返缩放 | 3.1–4.6ms |
| 同时拖动 50 张图 | 1.7–3.0ms |
| 中景快速甩动 | 0.3–5.7ms |

200 张图的 L0 全部上屏需要 150–280ms；峰值纹理显存约 830MB；不限帧率时每秒能渲染 900–1700 帧；强制 2 倍像素密度同样达标；打包后的 .app 为 279MB，其中 `app.asar` 2.1MB。

### M1 项目与图像卡 ✅
新建和打开项目目录；拖入或粘贴导入图片；图像卡和版本栈；命令系统、撤销重做、自动保存、缺失占位；三个区域和区域跳转；基础快捷键。
**验收**：导入 100 张图，关掉应用再打开，状态完全一致；撤销重做覆盖所有操作。

**实现要点**

- 文档是不可变快照，每次改动生成新的卡片数组；撤销栈只存前后两个快照的引用，覆盖所有操作且几乎不占内存。
- 拖动、缩放过程中的中间状态只给画布，不进撤销栈、不触发 React；松手时合成一条历史记录。面板只订阅提交后的状态。
- 自动保存：改动后 300ms、视口变化后 1 秒写盘；关窗前主进程会等渲染进程把未保存的改动写完（最多 3 秒）。
- 启动时自动打开上次的项目；"文件 → 最近项目"保留最近 10 个。
- 双击 `启动暗夜精灵.command` 即可启动（首次运行自动安装依赖，之后每次先构建再启动）。

**怎么验证**

| 命令 | 作用 |
|---|---|
| `npm test` | 22 个单元测试：文档操作、撤销重做、手势合并、项目文件校验、L2 切块 |
| `npm run check:m1` | 两次启动的验收自检（见下） |
| `electron . --capture=/tmp/x.png` | 开发用：启动 1.5 秒后截图退出 |

`check:m1` 第一次启动：通过真实的导入流程导入 100 张图，执行拖动、等比缩放、方向键微调、创建副本、重命名、导入为新版本、切换当前版本、移到最前、删除、跨区域移动共 10 种操作，然后逐步撤销 11 步回到空项目、再逐步重做 11 步，每一步都和记录的快照逐字比对，最后保存退出。第二次启动：重新打开同一个项目，和退出前的状态逐字比对，并确认没有缺失原图、全部缩略图可用、版本栈完整。

**结果**：全部通过。导入 100 张 2K 图约 4.2–4.5 秒（含缩略图和切块），重新打开后 100 张缩略图 130–170ms 全部上屏；M0 的性能测试在新的文档模型下仍然达标。

### M2 生成 ✅
OpenAI 供应商（API Key 存钥匙串）；提示词卡、来源连线、`{{Image N}}` 绑定；后台生成队列（默认 2 张，可调 1–4 张）和费用估算；结果进入版本栈。
**验收**：完成"照片 → 简笔画 → 3D"两步链路，生成过程中画布不掉帧。

**怎么用**

1. 选中一张或几张图按 **P**：右侧新建一张提示词卡，按从上到下的顺序绑定为 Image 1、Image 2…，右侧面板的提示词框自动获得焦点。
2. 在右侧面板写提示词（画布上的卡片实时跟着变），设数量、质量、尺寸；尺寸默认"跟随输入图"的比例。
3. **⌘↩** 生成。第一次生成会在提示词卡右侧新建输出图像卡，之后再生成都追加进它的版本栈。
4. 想换一张输入图：从提示词卡左侧的 ⊕ 拖一条线到别的图像卡上；顺序和解除绑定在右侧面板里调。
5. 设置（⌘,）里选 OpenAI 或本地模拟、填 API Key、选模型、测试连接。

**实现要点**

- OpenAI（2026-11 的接口）：有输入图走 `/v1/images/edits`，输入图先由图片工作进程缩到长边 2048 的 PNG，以 base64 放进 JSON；没有输入图走 `/v1/images/generations`。默认模型 `gpt-image-2.6-flare`，可选 2.6 sunburst 和 2.5 系列。
- 费用：生成前按 gpt-image-2 的价目表粗估（官方没公开 2.5 / 2.6 每张图的 token 数）；完成后按返回的 `usage` 用 $8 / $5 / $30 每百万 token 算实际花费，并用实际 ÷ 粗估更新校准系数（按模型和质量分别记，指数滑动平均）。
- API Key 用 `safeStorage` 加密存在 userData，解密密钥在系统钥匙串里；Key 只在主进程使用。
- 生成队列在主进程，最多同时跑 2 个，可取消；切换项目时取消未完成的任务。
- 生成结果是永久改动（ADR 0005）：撤销只会切回当前版本，生成的版本不会丢。
- 每个生成的版本都记下提示词全文、各输入图当时的版本、模型、尺寸、质量和分摊花费，为第二版的"已过期"判断做准备。

**怎么验证**

| 命令 | 作用 |
|---|---|
| `npm test` | 34 个单元测试（新增：提示词卡操作、生成结果追加与幂等、撤销不丢版本、尺寸限制、提示词渲染、花费计算） |
| `npm run check:m2` | 两次启动的验收自检，用本地模拟供应商，不花钱 |

`check:m2` 第一次启动：画布上先放 60 张图增加负担；选中照片按 P、写"转简笔画"提示词、生成 2 张；选中结果按 P、写"转 3D"提示词，同时提交两个任务；生成全程让画布持续平移并记录每一帧。然后撤销到底，确认生成的版本还在；再全部重做，和撤销前逐字比对。第二次启动：重新打开，核对状态、五段链路、生成记录和缩略图。

**结果**：全部通过。整条链路约 3.5–5 秒（本地模拟）；生成期间最慢一帧 CPU 1.8–6.6ms，超过 20ms 的帧间隔 1–2 帧（共 200–300 帧，低于 1%）。

**还没验证**：真实的 OpenAI 调用。本机没有 API Key，代码按 2026-11 的接口文档实现；拿到 Key 后先在设置里点"测试连接"（不花钱），再用低质量、1 张试一次。

### M3 视觉主题与助手 ✅
主题卡；生效主题卡自动附加规则（可单次关闭）；助手面板支持生成主题卡、反推参考图、批量写提示词卡，只放卡片、不发起生成。
**验收**：助手根据"日式寿司点餐"生成主题卡，四个金刚位的提示词卡一次写好。

**怎么用**

1. ⌘J（或右侧面板顶部的"助手"）打开助手。点"生成主题卡"，改一下引号里的产品主题，回车。主题卡出现在视觉主题区；项目里第一张主题卡自动生效。
2. 选中四个金刚位，点"给选中的图各写一条提示词"，补一句要求（比如"3D 图标风格"）回车：四张提示词卡在这些图右侧排成一列，各自绑定一张图（每张卡里都是 Image 1）。
3. 选中参考图点"反推选中的图"：得到按「画面主题／构图／造型与材质／光线／色彩」分段的提示词卡，可以直接复用它的风格。
4. 主题卡在右侧面板里逐项可改：产品主题、关键词、线索、配色（取色器 + 角色 + 用途）、造型 / 材质 / 光影 / 色彩协调四条规则；"设为生效主题卡"切换生效的那一张。
5. 每张提示词卡的生成参数里有"附加生效主题卡的规则"开关，可以展开看附加的原文。

**实现要点**

- 助手走 OpenAI Responses API（`/v1/responses`），严格模式的 JSON Schema 结构化输出：一次回答可以同时包含回复文字、一张主题卡草稿和若干提示词卡草稿；返回后再做一遍业务校验（颜色必须是 #RRGGBB、绑定序号在范围内、最多 12 张）。默认模型 `gpt-6.1-terra`（2026-10 发布，看图快，$1 / $5 每百万 token），设置里可换 6.1 Sol、6 Luna、6 Astra。
- 选中的图（最多 8 张，按从上到下、从左到右排序）缩到长边 1024 一起发给助手；生效主题卡、选中的提示词卡和最近 8 轮对话作为文字上下文。对话只在内存里，换项目清空。
- 助手一次回答新建的所有卡片是一条撤销记录。
- 生效主题卡是文档状态（`activeThemeCardId`，可撤销）；生成时把主题卡转成固定格式的一段文字附加在提示词末尾，版本记录里的提示词全文包含它，并记下用的是哪张主题卡（`themeCardId`），为"已过期"判断做准备。
- 本地模拟助手内置想法文档里"日式寿司点餐"的那套方向（新鲜 / 热闹 / 亲切 / 有食欲；寿司、餐盘、轨道、IP 形象、红色；金枪鱼红、玉子橘黄、海苔墨、米饭暖白）。

### M4 页面与导出 ✅
导入低保真原型；页面框（默认跟随原型尺寸，也可以选设备预设）；摆放引用核心素材，并跟随当前版本；导出 PNG、素材包、分层 SVG。
**验收**：完整跑通第 2 节的寿司用例，导出的 SVG 在 Figma 里图层清晰、图片完整。

**怎么用**

1. "页面 → 从低保真原型新建页面框…"（⌘⇧L）选一张线框图，页面框出现在高保真页面区；尺寸正好是设备 1/2/3 倍的会自动认出（比如 1179 × 2556 → iPhone @3x）。也可以按 F 新建空白页面框。
2. 把核心素材拖到页面框上，页面框变绿时松手：原图回到原处，页面里多出一个素材引用（比页面大时缩到 90% 宽）。按住 ⌥ 拖则只是普通移动。也可以在图像卡的属性里"放进页面"。
3. 引用和普通卡片一样拖动、拉角缩放、方向键微调；拖动页面框时里面的引用一起动。
4. 在核心素材的版本栈里换当前版本，所有页面里的引用跟着换。
5. 选中页面框按 ⌘⇧E（或属性里的"导出页面"）：写到 exports/页面名/，包括 page.png、page.svg、assets/ 下每个素材的 @1x/@2x/@3x 和 manifest.json（逻辑坐标）。属性里可以换设备、导出倍数、背景色、替换低保真原型。

**实现要点**

- 素材引用是独立的卡片类型（ADR 0006），页面框与引用之间的级联规则都在 `operations.ts`，有单元测试。
- 画布上图像卡、引用、页面框（低保真原型）共用同一套纹理绑定：每张卡片绑定"它要显示的版本"，引用在被引用图像卡换版本时自动换绑。
- 导出坐标在共享模块里按"页面宽度 → 逻辑宽度 × 导出倍数"换算（`planPageExport`），整页 PNG、SVG 和素材包都由图片工作进程用 sharp 生成；超出页面的部分在 PNG 里裁掉，SVG 里保留完整图层。

**怎么验证**

| `npm test` | 46 个单元测试（新增设备识别、页面级联、绘制顺序、引用跟随版本、导出坐标） |
| `npm run check:m4` | 完整跑一遍寿司首页（本地模拟助手 + 本地模拟生成），两次启动 |

`check:m4` 第一次启动：助手生成主题卡并生效 → 导入 Banner 参考和四个金刚位参考 → Banner 写提示词、四个金刚位由助手一次写好提示词，五个任务一起生成 → 用一张 iPhone 3 倍的首页线框新建页面框 → 五个结果放进页面（Banner 盖住线框的 Banner 区，四个金刚位盖住四个圆），检查原图不动、一步撤销 → 给"热门寿司"再生成一张，检查页面里的引用换成新版本 → 导出，检查 PNG 1179 × 2556、SVG 五层且层名正确、素材包齐全。第二次启动：重新打开逐字核对，再导出一次。

## 9. 风险

| 风险 | 应对 |
|---|---|
| Electron + PixiJS 达不到 120fps | M0 已验证达标；整张 2048 纹理上传会超预算，已改为 L2 预先切块（ADR 0004） |
| 还没在真正的 120Hz 屏上实测 | 拿到 ProMotion 屏后跑一次 `npm run bench`，看帧间隔 p99 |
| 生成结果到达时偶有 1–2 帧间隔超过 20ms（帧内 CPU 只有几毫秒，时间花在帧外：结果写入文档后面板重渲染、保存） | 已用 memo 隔开面板和每秒 4 次的状态刷新；仍出现就把结果写入拆到空闲时段 |
| OpenAI 真实调用（生图和助手）未经实测 | 拿到 Key 后先"测试连接"，再低质量单张试跑、问助手一次 |
| M2 自检里生成期间超过 20ms 的帧在 1–3 帧之间波动（约 300 帧里），贴近 1% 的门槛 | 下一步把生成结果写入文档、面板更新放到空闲时段 |
| 单张 L1（1024）上传偶尔到 8.5ms（M1 回归测试中 4 次里出现 1 次，其余 2.5–6ms） | 继续观察；如果在 120Hz 屏上掉帧，L1 也改成切块上传 |
| 偶发长帧：M0 期间有一次 272ms，之后 10 次以上没再出现 | 报告里保留每帧分段计时（脚本 / 视口 / 调度 / 提交 / 渲染），再出现时直接定位 |
| `sharp` 等原生模块在 Electron 下打包麻烦 | M0 已验证：`asarUnpack` 之后，打包的 .app 自检通过 |
| 生图费用失控 | 每次生成前显示估算，队列里显示累计花费，助手不会自动生成 |
| 原图占内存 | 原图只在 L2 级别、且在视口内时加载 |
| 分层 SVG 导入 Figma 后丢失结构 | M4 用真实的 Figma 导入来验收 |
